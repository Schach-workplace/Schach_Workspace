## Important

1. **Ordinary refresh dismisses an open native calendar and loses its unconfirmed selection.** `mobile/src/SavedReports.tsx:154` makes `locked` depend on fresh source reads; `mobile/src/SavedReports.tsx:268` passes that to `pickerDisabled`. `mobile/src/DeadlinePicker.tsx:114` removes the mounted native picker whenever it becomes true, and line119 clears mode on dismissal. This contradicts the required retained authored picker/sheet shell during ordinary same-company reauthorization (plan lines50,224). The controller's exact-HEAD evidence `/tmp/schach-roadmap-native-runtime-20261011/m6-native-calendar-hold.json` shows Saved start date / selected10Oct2026 present at1.99s and absent at7.99,13.99,19.99s without another action. Preserve the mounted picker and local pending choice through this temporary barrier; disable confirmation/business submission and hide fetched choices. Confirmed denial and principal/background changes must still dismiss/purge it. The existing authored-name IME pass remains valid for that separate input.

2. **Event limits can silently truncate a filtered snapshot.** `backend/platform/report_history_reads.go:181` and line194 fetch only the first10,001 acceptance/time facts per100-task batch, then apply historical dimension filters in Go at lines186 and205. There is neither pagination nor a fetched-limit overflow check. For example,10,001 earlier entries attributed to ownerA followed by a matching ownerB entry in the same batch produce an apparently complete ownerB report that omits its hours. The combined output-row check at line112 never catches discarded candidates. Apply attribution filters before limiting, or iterate bounded pages until exhaustion/the actual output cap; return an explicit range error if candidate completeness cannot be established. The separate all-visible-task cap at lines40–44 also rejects a narrow filtered report once the company has10,001 readable tasks, so the advertised instruction to narrow filters cannot recover that case. This violates the plan's explicit no-silent-truncation requirement at line25.

3. **Lost-ACK replay and reconciliation can silently attach old authored fields to an unseen newer CAS version.** Saved writes read the current definition after canonical replay (`backend/platform/saved_reports.go:252`; create has the same pattern at line189), and schedule writes read current rows (`backend/platform/report_schedules.go:196`). Both clients unconditionally replace their captured version from that response while preserving authored configuration/schedule (`frontend/src/components/SavedReports.tsx:160`, line184; `mobile/src/SavedReports.tsx:177`, line204). Concrete sequence: version1→2 commits but its ACK is lost; another session writes version3; retry returns current version3; retained version1/2-authored fields now save against3 without human reconciliation. Additionally, “Reconcile current definition” changes `scheduleVersion` but never replaces the authored schedule fields (`frontend/src/components/SavedReports.tsx:491`, `mobile/src/SavedReports.tsx:545`), so a later schedule save can overwrite an uninspected intervening schedule. Preserve canonical committed versions separately from current fetched revisions and require explicit reconciliation before rebasing retained fields; when choosing replacement, replace the schedule together with its version. Add lost-ACK/intervening-write and schedule-reconciliation cases on both clients (plan lines208,223,232).

4. **One failing recipient capture can indefinitely starve every later due schedule.** `backend/platform/report_schedules.go:273` rolls back the entire schedule when one recipient's capture fails; line286 does the same when the owner's full-manifest authority fails, and line305 returns from the entire ordered maintenance pass. Its next occurrence remains due, so the same earliest schedule fails again each pass. A recipient who cannot read an explicitly selected project, a recipient whose scope exceeds the report cap, or a recipient whose included task is unreadable by the owner can block otherwise valid recipients and unrelated companies' later schedules. The worker also discards this error (`backend/platform/report_runtime.go:205`), leaving no operational diagnosis. Isolate recipient outcomes, record terminal authorization/limit failures without exposing sources, and continue other due schedules; transient errors need bounded retry/backoff and visible diagnostics. Verify a bad first schedule alongside a valid later schedule, and mixed eligible/ineligible recipients within one definition.

5. **Scheduled outputs remain eligible after their owner becomes a viewer.** `backend/platform/report_export_jobs.go:40` checks active ownership, then lines52–56 refresh the owner and validate configuration, but neither checks the owner's management role. `validateSavedConfiguration` has no role restriction. Consequently queued generation, publication, delivery and ready downloads can continue after an owner is demoted to viewer. The role check exists only in the due-schedule scan (`backend/platform/report_schedules.go:236`); a next-week schedule will not reach it for days. Enforce current owner management eligibility in the common job authorization fence and cancel/pause obsolete automated work. This is required by the plan's owner-loss checks at lines193,197; permission to read a personal snapshot does not preserve permission to run its schedule.

6. **Web CSV completion is not fenced by same-key reauthorization or job denial.** The download completion guard only checks abort and `[company,user,readBasis]` (`frontend/src/components/HistoricalReports.tsx:57`, line156). Its abort effects cover scope/background/unmount and `result.denied`, not `!result.ready`, `!job.ready`, or `job.denied` (lines87–96). An ordinary work event invalidates reads without changing that scope (`frontend/src/data/execution.ts:89`); a CSV already in flight can therefore create a download URL while current checks are pending. A denied job makes `snapshotId` empty at line55, disabling historical reads, so `result.denied` need not ever become true. Use a current readiness/generation fence and cancel/discard the transfer on every relevant pending/denied lane; reauthorize before publication as the native transfer does. Server chunk fencing cannot recall already-in-flight bytes and does not replace this required cooperative-client guard (plan line209).

7. **The PostgreSQL precision-preservation heuristic overwrites legitimate exact deadline edits.** `backend/platform/report_facts.go:47` treats any microsecond-aligned value equal to the previous value truncated to a microsecond as an unchanged reload. A deliberate deadline edit from `...00.000000001Z` to `...00Z` therefore stores the previous `...001Z` in the new fact at line48. It loses the actual current commitment, can misclassify exact-boundary on-time acceptance, and differs from SQLite. The accepted patch path still knows whether `dueAt` was explicitly authored (`backend/platform/task_mutations.go:74`), so this is not an unavoidable limitation: pass that provenance to fact construction, preserve old exact strings only for unchanged reloaded fields, and retain new exact input for real edits. The implementer's disclosed limitation does not satisfy the explicit raw-exact timestamp requirement (plan line85). Add PG/SQLite parity for an intentional nanosecond-to-microsecond-aligned revision.

8. **A resolved history gap inside the requested period disappears from coverage.** `backend/platform/report_history_reads.go:147` emits a gap only when the report's end cutoff itself lies within that gap. For a September10–20 skipped-version interval and a known September20 state, a September1–30 snapshot emits no `coverage.gaps` row. The later exact state is correctly usable as-of cutoff, but unrecorded acceptance/effort/state changes within the month remain unknown; recovering a later state cannot establish that intervening history. This also leaves period comparisons with no such coverage warning (`backend/platform/report_history.go:163`). Separate cutoff-state availability from interval-overlap coverage: retain the known cutoff state and add a coverage row for each relevant unknown interval intersecting the period. Verify an interior gap, a cutoff within a gap, and a gap entirely outside the period (plan durable coverage contract at line84).
