# New Breakage in the Fix Diff

- **Important — Nonexistent local midnight can silently omit actual timed commitments while claiming a complete range.** `backend/platform/planning_calendar.go:68`, `:72`, `:76`, `:95`, `:160`. `ParseInLocation` does not guarantee that midnight exists on the requested civil date; Go can normalize it into the previous date. `last.AddDate(0,0,1)` then advances that normalized date and hour rather than constructing the correct exclusive boundary for the requested final date. For supported company timezone `America/Havana`, week `from=2026-03-02&to=2026-03-08` crosses the midnight spring transition: parsing the final date gives `2026-03-07T23:00:00-05:00`, and the computed upper boundary becomes `2026-03-09T03:00:00Z`. A valid current timed Task at `2026-03-09T03:30:00Z` has company date `2026-03-08`, but SQL excludes it and the response nevertheless sets `complete:true`. Both database paths use this same incorrect upper instant. With only that visible task, the Calendar reports a false zero for the selected Sunday. A single-day March7 request likewise excludes the final hour; a March8 start can include the previous day's final hour, allowing irrelevant-date tasks to affect the selected cap. Company validation allows arbitrary valid IANA zones (`backend/platform/organization.go:54`), so this is within the accepted contract. Original0ad's instant-to-company-date filtering did not introduce these midnight boundary exclusions. Compute boundaries from the requested civil dates with explicit handling for midnight gaps/overlaps/skipped dates, and ensure candidate timed rows have the selected company dates before caps/completeness. Add covering SQLite/PG tests for a midnight transition, including a week ending on that transition day. The existing NewYork test (`backend/platform/planning_calendar_test.go:133`) transitions at02:00 and does not cover this case.
