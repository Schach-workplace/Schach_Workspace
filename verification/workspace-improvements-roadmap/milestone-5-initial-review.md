#### Important (Should Fix)

1. **Native schedule picker overwrites the newly selected commitment.** `mobile/src/Execution.tsx:147` calls `setDate`, `setTime`, then `setInstant` from one picker event. In `ScheduleDeadline`, `:585`, `:593` and `:602` each publish a full commitment computed from the same old render's date/time. The last callback therefore restores the old date/time. A focused execution of these actual diff functions selected `2026-10-22` from an all-day `2026-10-10` row and produced updates for October 22, October 10, October 10; final date was October 10 (assertion exit 1). Timed edits also risk restoring old values or throwing from the unguarded final `workDeadline`. Publish one atomic update using the new date/time/instant tuple and exercise the real picker callback; current execution UI tests replace DeadlinePicker with null (`mobile/src/Execution.test.tsx:36`).

2. **A changed submission basis permanently strands an in-review milestone.** `backend/platform/project_milestones.go:595` applies the submitted-project/task equality checks to both approval and request_changes. After an allowed time entry bumps any submitted task version, or any project edit bumps its version, both decisions return 409 forever. Editing requires draft (`:431`), submit requires draft (`:551`), and reopen accepts only accepted milestones (`:627`). There is no route back to draft for fresh inspection. Preserve strict approval checks, but provide an authorized, versioned, reasoned reset/reopen path for stale in-review submissions. The exact-basis guard on request_changes is **plan-mandated** (`docs/superpowers/plans/2026-10-11-task-project-execution.md:126`); the resulting state-machine dead end still requires a design correction, not weakening independent approval.

3. **Definitively rejected browser mutations become unrecoverable frozen forms.** `frontend/src/data/execution.ts:141` freezes every attempted payload, but `:166` clears it only for 401/403/404. A 422 validation rejection or 409 stale inspected version leaves the attempt indefinitely locked. Forms disable edits while an attempt exists (`frontend/src/components/ProjectMilestones.tsx:121`, `frontend/src/components/TaskTemplates.tsx:339`), and the web adapter exposes no abandon/reconcile action. Retry always resends the rejected old values. Ordinary web create has the same retention in `frontend/src/components/TaskDrawer.tsx:313`. Distinguish definite noncommits from unknown transport outcomes and allow deliberate correction/reconciliation; keep unknown outcomes bound to their original key. Add a browser regression for stale-version and validation-error recovery.

4. **Browser schedule recovery can display one proposal while submitting another.** `frontend/src/components/ScheduleReview.tsx:40` stores the fetched proposal/reference only in component state, while the apply attempt survives remount in shared RAM (`:22`). After a lost apply response and closing/reopening the drawer, the proposal ID is lost and the original confirmation is inaccessible. The UI instead permits making a fresh preview. Its confirmation displays the fresh proposal (`:293`) but `frontend/src/data/execution.ts:141` silently chooses the previous apply attempt and posts the old proposal ID (`:156`), ignoring the displayed new intent. Preserve the selected proposal ID in scoped RAM or recover it from the frozen apply payload; fetch and display that exact proposal before permitting retry, and prohibit a new review from silently using the old attempt.

5. **Browser template editing stays live during source reauthorization and can turn an edit into creation.** `frontend/src/components/TaskTemplates.tsx:338` and `:457` render management fields/actions independently of `detail.ready`. During a background/same-key recheck, `source` becomes undefined but copied source names/defaults remain visible and Save remains enabled (`:464`). At `:491`, `!!source && editingTemplate` becomes false, so Save sends POST `/task-templates` without a version instead of PATCH to the inspected template. This can create a duplicate while the original source is being reauthorized, and violates the fetched-content hiding requirement. Keep operation/source identity captured independently of fetched availability, hide fetched defaults while pending, and disable writes until current source access succeeds. Preserve only authorized authored RAM across the barrier.

6. **Browser project reauthorization discards authored milestone forms and can make unknown saves unreachable.** `frontend/src/pages/Projects.tsx:63` replaces the whole project subtree whenever the current query hides data. The milestone selection/creating flags (`frontend/src/components/ProjectMilestones.tsx:26`) and fields/captured versions (`:91`) are only local useState, so background/resume or a same-key invalidation unmounts them and loses the draft. If a save outcome is unknown, its shared attempt survives but the remounted blank form is locked and its retry button is disabled by empty title/criteria/selection (`:233`). Persist authored input and captured basis in scoped RAM, retain a reachable frozen-attempt retry, and keep fetched records hidden while reauthorizing. The native shell fix does not fix this browser path.

Merely renaming a template that deliberately has no relative deadline now makes future task applications due on the anchor date. This contradicts the final follow-up's preservation of typed defaults. Preserve absence separately from zero, omit the field when unset, and include the absent-offset case in the existing rename regression.
