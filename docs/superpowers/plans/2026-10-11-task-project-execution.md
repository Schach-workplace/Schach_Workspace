## Global Constraints

- “Finance retains exact amounts, independent review, receipt exceptions and recorded overrides.”
- “Task changes retain original deadlines, evidence requirements, independent acceptance and optimistic versions.”
- “Keep Go/GORM/Encore/PostgreSQL and React/Expo.”
- “Do not introduce a second task engine, unrestricted global search, autonomous AI approvals or a microservice fleet.”
- “India remains the deployment region.”
- “Idempotent action keys survive transport retries”; every new template/schedule mutation requires them (including persisted schedule previews). Read-only previews and GETs create no work. Existing unkeyed task-create/import APIs retain compatibility and remain explicitly unsafe to repeat. All updated first-party task creation/import controls send keys.
- Company/task/project access never grants private conversation membership, history or source revisions. Ordinary templates accept no private message/conversation/source-link fields. Keep existing CommunicationRetry and publication-audience contracts unchanged.
- Current access precedes canonical replay; immutable task originals never appear in patch columns. Accepted tasks remain frozen until the existing reviewed reopen workflow. No goal measurement or Goal.Current update is triggered by task or milestone completion.
- Touch targets at least 44 logical pixels, 320–430px phone layouts, safe area/keyboard handling, labelled inputs, recoverable failures. Authored drafts remain RAM-only; fetched content is hidden pending same-key reauthorization and on background/scope change.
- Preserve the running main app/database. Use isolated owned fixtures for later checks; physical devices, push, signing and production capacity remain separate rollout gates.

## Review Focus

1. A task is reassigned or a template's scope is removed while membership is unchanged: current detail, preview, apply and replay deny or purge inaccessible data (Tasks 1, 3, 5–7).
2. A server commit succeeds but its response or subsequent refresh fails: retry preserves payload/key and returns the original result without another code, checklist append, acceptance or schedule write (Tasks 1–7).
3. A dependency, time entry or evidence version changes after inspection: schedule/milestone acceptance conflicts, preserves original commitments, and requires a fresh human review (Tasks 4–7).
4. Only part of a project graph is visible: impact paths contain exclusively visible nodes; project progress labels its authorized coverage; hidden work is neither counted nor moved (Tasks 4–7).
5. Company midnight, DST ambiguity, background/resume or a phone keyboard interrupts an action: the frozen concrete deadline remains stable, authorized input survives, stale fetched content does not, and the primary action remains reachable (Tasks 2, 3, 5–7).
